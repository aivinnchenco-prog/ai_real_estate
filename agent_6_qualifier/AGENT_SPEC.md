# Agent 6 — Qualifier · Agent 7 — Envoy · Agent 8 — Notary

Спецификация зафиксирована по итогам обсуждения. Источник правды по объектам — Notion CRM
(`Аренда недвижимости`, db `e817ce50-e788-4992-8b86-c9c9fc1fbcf7`). Канонический формат **Объект ID**:
`F_YYYYMMDD_NNN` (источник Facebook), `A_YYYYMMDD_NNN` (источник Airbnb).

> **Карта ролей и legacy-имён:** корневой [`ROLE_MAP.md`](../ROLE_MAP.md).
>
> **Важно:** canonical Python-пакеты — `agent6_qualifier` (Qualifier), `agent7_envoy` (Envoy),
> `agent8_notary` (Notary). Пакеты `agent7` и `agent8` — **legacy compatibility shims** (thin
> re-export); старые импорты продолжают работать. Runtime в `agent_6_qualifier/`.

**Три роли живут в этом проекте:**

| Целевая роль | Canonical package | Legacy shims | Основные модули |
|--------------|-------------------|--------------|-----------------|
| Agent 6 Qualifier | `agent6_qualifier` | `agent7.*` | `qualifier.py`, `tg_userbot.py`, `matching.py`, `brain.py` |
| Agent 7 Envoy | `agent7_envoy` | `agent8.*`, `agent8.envoy.*`, `agent7/airbnb_check`, `agent7/owner_registry` | `auto.py`, `outreach.py`, `calendar_check.py`, `owner_result.py`, owner-шаблоны в `agent6_qualifier/templates.py` |
| Agent 8 Notary | `agent8_notary` | `agent8.booking_doc`, `agent8.notary.*`, `agent8.notary_service` + `scripts/generate_booking_request.js` | docx брони, прикрепление к amoCRM |

Общие модули (Notion, модели, amoCRM, шаблоны клиента) — в `agent6_qualifier`; Envoy и Notary их переиспользуют.

|--|--|--|--|

(`agent8_notary.booking_doc.generate_booking_doc`; legacy: `agent8.booking_doc`): docx клиенту + `amo.attach_file`.

## 2. Каналы связи (единые контакты)

- **Один и тот же** WhatsApp-номер и TG-аккаунт для клиентов и собственников. Разделение:
  - WhatsApp: ярлык (label) `клиент` / `собственник` на чате;
  - Telegram: чат добавляется в папку `Клиенты` / `Собственники` (управляется userbot'ом через MTProto).
- **Telegram — личный аккаунт (userbot, Telethon/MTProto), НЕ бот.** Личный аккаунт вызывает больше доверия.
- WhatsApp: провайдер с API и синхронизацией с amoCRM (Wazzup / Green-API).
- Вся переписка зеркалится в amoCRM (синхронизация WA/TG ↔ amo), но поля квалификации агент пишет в сделку **явно**.

если Agent 4 уже записал mapping в Notion (`post_url_*`, `metricool_post_id`).

Модули: `publication_resolver.py`, `publication_mapping_store.py`, `telegram_publication.py`.

## 4. Диалог с клиентом (Qualifier)

Мягкий, короткий диалог; критерии собираются компактно, без длинной анкеты отдельным
сообщением на каждый вопрос.

1. Клиент **без выбранного объекта** и **без явного запроса на подбор** (и без уже
   названных критериев) сначала получает вопрос: **конкретный объект с наших ресурсов
   или подбор по запросу?**
2. Если клиент выбрал конкретный объект, но не прислал ссылку/ID — просим ссылку на пост
   или номер объекта (например `#A_20260713_003`).
3. Qualifier отправляет **единую анкету одним сообщением**:
   - бюджет в месяц;
   - район;
   - количество спален;
   - дата заезда;
   - дата выезда *(не указывать, если контракт на год)*.
   Если объект уже найден в Notion, в том же сообщении **подтверждаются данные объекта
   из таблицы** (тип жилья, спальни, район) — **без цены**.
4. **Дата заезда** — минимально обязательное поле для проверки доступности и расчёта цены.
   Пока заезд не указан, отдельно запрашиваем его.
5. **Дата выезда не указана** трактуется как **годовой контракт** (переспрашивать выезд
   не нужно).
6. **Цену не называем до получения даты заезда** — она зависит от `monthly_prices` на
   соответствующий период. После даты заезда один раз сообщаем **ориентировочную цену
   на период**.
7. После квалификации — ссылки на TG-пост, фото R2 и карту (один раз).
8. Перед показом альтернатив — **обязательно спросить**, нужны ли они.
9. Животные, имя и прочее — по ходу диалога, точечно.

Поля квалификации: даты заезда/выезда, срок, бюджет (+ допустимая погрешность), район,
кол-во спален, гостей, животные, имя.

Клиенту отправляем по объекту:
- ссылку на пост в TG-канале (`post_url_telegram`);
- ссылку на фото из R2 (колонка `Фото` в Notion);
- локацию на карте (`Google Maps`), если есть;
- краткое «почему подходит» при альтернативах;
- **ориентировочную цену на период** — только после даты заезда, не при первом
  подтверждении объекта.

## 5. Подбор альтернатив (фильтры, по жёсткости)

1. Пересечение дат / тип аренды; объект не `занято` по availability.
2. **Бюджет ±10%.** Если кандидатов мало — спросить клиента, какая погрешность по бюджету допустима, и расширить.
3. Район клиента (или соседние из whitelist).
4. Вместимость ≥ числа гостей (прокси — комнаты, пока нет отдельного поля).
5. Животные: если pets = да → подходят объекты `Можно с питомцами = да` **и объекты с пустым полем** (не указано ≠ нельзя).
6. Похожесть на выбранный объект: тип жилья, комнаты ±1.

## 6. Занятость объектов (availability, Envoy)

Новые колонки в Notion (напротив объекта):

| Колонка | Тип | Значения |
|--|--|--|
| `availability_status` | select | `свободно` / `занято` / `уточняется` |
| `Занято до` | date | до какого числа занят |
| `Будущие брони` | rich_text | периоды будущих броней, если владелец сообщил |
| `availability_checked_at` | date | когда проверяли последний раз |
| `Свободно` | checkbox | отметка внешнего агента-актуализатора: галочка = доступность подтверждена; снятая = нет информации (НЕ «занято») |
| `Календарь` | url | где автоматически проверять доступность дат (pre-check Envoy) |

Правила заполнения `Календарь` (в зависимости от источника объекта):
- объект с **Airbnb** → ссылка объявления дублируется в «Источник объявления» и в «Календарь»;
- объект от **управляющей компании** → в «Календарь» ссылка на их календарь занятости;
- календаря нет (**ручной** способ: FB Marketplace и т.п.) → «Календарь» пуст,
  доступность уточняется только сообщением владельцу через Envoy.
Pre-check Envoy всегда идёт по «Календарь»; пусто — сразу пишем владельцу.

Поддерживаемые типы ссылок в `Календарь` (диспетчер `agent7_envoy.calendar_check`; legacy: `agent8.calendar_check`):

| Тип ссылки | Как проверяем | Статус |
|--|--|--|
| Google Sheets УК (`docs.google.com/spreadsheets/...#gid=вкладка_объекта`) | xlsx-экспорт: красная заливка = занято, жёлтая = «под вопросом» (уточнить у владельца), без заливки = свободно; вкладка объекта находится по gid | работает |
| iCal `.ics` (Airbnb ical, Booking, экспорт GCal) | скачиваем фид, пересечение ночей клиента с VEVENT | работает |
| Google Calendar (embed-ссылка с `src=`) | конвертация в публичный iCal-фид | работает |
| Airbnb-объявление | Playwright, чтение календаря страницы | этап 4 |

Проверяются **ночи** [check_in, check_out): выезд в день чужого заезда — не конфликт.
Даты за горизонтом календаря / сбой проверки → «неизвестно», пишем владельцу как обычно.

Правила согласования `Свободно` и `availability_status`:
- галочка стоит и статус не «занято» → объект считается подтверждённо свободным;
- Envoy при записи статуса сам синхронизирует чекбокс («свободно» → ставит, иначе снимает);
- внешний агент-актуализатор может работать только с чекбоксом — код это учитывает.

Самообучение системы: когда Envoy узнаёт от владельца, что объект занят, он **обязан** уточнить:
до какого числа занято, когда освободится, есть ли брони в будущем и на какие даты — и записать это в Notion.

**Занято на нужные даты — не тупик:** клиенту сообщаем, до какого числа объект занят и с какой
даты будет свободен («Этот объект занят до X, свободен с Y — подойдут такие даты?»).
Если клиента не устраивает — предлагаем альтернативы.

**Airbnb pre-check:** если `Источник объявления` — ссылка Airbnb, то **до** письма владельцу
Envoy проверяет открытые даты в календаре объекта по этой ссылке (headless-браузер Playwright,
как в Agent 1B; вариант — делегировать Clawbot/OpenClaw). Результат тоже пишется в колонки availability.
Если даты клиента закрыты в календаре — владельцу не пишем, клиенту сразу предлагаем альтернативы.

Pre-check распространяется и на **альтернативы**: перед тем как предлагать клиенту / писать
владельцу по альтернативному объекту с источником Airbnb, сначала проверяем его календарь.
Объекты с закрытыми датами отсеиваются, результат проверки пишется в availability-колонки.

## 7. Связь с владельцем: приоритет каналов и скрипты (Envoy)

Приоритет: **1) WhatsApp → 2) Telegram → 3) Airbnb DM → 4) FB Marketplace DM** (берём первый заполненный в Notion).

**WhatsApp / Telegram / FB Marketplace** — первое сообщение передаёт:
- ссылку на объявление владельца или идентификатор объекта (чтобы он понял, о каком жилье речь);
- дату заезда и выезда **или** формулировку **годового контракта**, если выезд не указан;
- количество гостей;
- вопрос о доступности на эти даты.

> Пример смысла: «Здравствуйте! Я менеджер от агентства … У меня есть клиент на ваше жильё
> [ссылка], готов заселиться с … по … / контракт на год. Гостей: N. Подскажите, свободны ли
> эти даты?»

**Бюджет клиента собственнику не сообщается** — внутренняя информация для подбора и торга.

**FB Marketplace — дополнительно:** сразу попросить WhatsApp для связи. Полученный номер немедленно
записать в Notion (`WhatsApp контакт`) и в amoCRM, дальше общаться в WA.

**Airbnb — другой скрипт** (про клиента не пишем, контакт напрямую НЕ просим):
1. > «Здравствуйте! Меня интересует ваше жильё. Можно посмотреть дом?»
2. После ответа:
   > «Посмотрите моё изображение-аватар.» (на аватаре аккаунта — наши контакты WA и пр.)

Дальше ждём, что владелец сам выйдет на нас в WA/TG; общение продолжается там и фиксируется в CRM.

## 8. Документы по брони (Notary)

После подтверждения брони клиентом (`booking_confirmed` в `qualifier.py`):

1. **Agent 8 Notary** формирует двуязычное **соглашение о бронировании** (docx) — заявка на объект и даты, порядок следующих шагов.
2. Документ отправляется клиенту в том же канале (TG userbot).
3. Копия прикрепляется к сделке amoCRM (`amo.attach_file`).
4. Данные агентства берутся из `config/project.json` → `agency`.

**Это не договор аренды и не договор оплаты.** Итоговые условия и оплата оформляются отдельным договором после показа и согласования с владельцем — полноценный шаблон такого договора **ещё не реализован**.

Код: canonical `src/agent8_notary/booking_doc.py` (legacy shim: `src/agent8/booking_doc.py`), `scripts/generate_booking_request.js`, выход — `data/contracts/`.

## 9. Воронка amoCRM — «Аренда — лиды»

Стадии:
1. **Новый лид**
2. **Квалификация**
3. **Подбор** (предлагаем варианты)
4. **Запрос владельцу** (ждём Envoy)
5. **Согласование условий** (сдвиг дат/цены, клиент думает)
6. **Бронь подтверждена** → Notary генерирует docx
7. Закрывающие: **Успешно** / **Отказ** / **Не целевой**

Поля сделки: `Объект ID`, даты заезда/выезда, бюджет (+ допуск), район, гостей, животные, имя,
`source_channel`, `preferred_object_id`, `alternative_object_ids`, ссылка на Notion-страницу, ссылка на TG-пост.

Правила «никого не терять»:
- на сделке всегда тег `OBJ_{object_id}`;
- контакт клиента и контакт владельца привязаны к **одной** сделке;
- примечания с префиксом `[OBJ:20260708_001][CLIENT]` / `[OBJ:...][OWNER]`;
- 1 клиентский диалог = 1 активная сделка; смена объекта = обновление поля, не новая карточка;
- дедуп лидов по телефону / TG username.

SLA-таймеры: 2 ч без ответа владельца → эскалация менеджеру; 24 ч без ответа клиента → мягкий follow-up.
Handoff человеку: тег `need_human` + задача менеджеру (торг, жалоба, «хочу созвон»).

## 11. Порядок внедрения (исторический; большая часть выполнена)

1. Колонки availability в Notion + воронка и поля в amoCRM.
2. Agent 6 Qualifier: приём сообщения → извлечение ID → квалификация → карточка amo.
3. Матчинг альтернатив + отправка TG-ссылок и фото R2.
4. Agent 7 Envoy: приоритет каналов, скрипты (включая Airbnb-скрипт), запись WA из Marketplace, Airbnb pre-check.
5. Замыкание цикла: ответ владельца → обновление availability в Notion → ответ клиенту.
6. Agent 8 Notary: docx брони + прикрепление к amoCRM (базовая реализация есть).
7. *(будущее)* Полноценный договор аренды; выделение Envoy/Notary в отдельные папки — см. `ROLE_MAP.md`.
