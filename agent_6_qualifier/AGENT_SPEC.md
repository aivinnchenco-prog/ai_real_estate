# Agent 7 — Qualifier (квалификация лидов) + Agent 8 — Owner Outreach

Спецификация зафиксирована по итогам обсуждения. Источник правды по объектам — Notion CRM
(`Аренда недвижимости`, db `e817ce50-e788-4992-8b86-c9c9fc1fbcf7`), `Объект ID` формата `YYYYMMDD_NNN`.

**Оба агента живут в этом проекте**: `src/agent7/` (диалог с клиентом) и `src/agent8/` (связь с собственником).
Общие модули (Notion, модели, шаблоны) — в `agent7`, Agent 8 их переиспользует.

---

## 1. Роли

| | Agent 7 — Qualifier | Agent 8 — Owner Outreach |
|--|--|--|
| Собеседник | Клиент (WhatsApp / Telegram) | Собственник (WA → TG → Airbnb → FB Marketplace) |
| Задача | Квалификация, подбор альтернатив, ответ клиенту | Проверка доступности, согласование дат/цены, вытянуть WA-контакт |
| Пишет в CRM | Лид + поля квалификации в amoCRM | Активность по сделке, обновление контакта владельца и занятости в Notion |

Agent 7 **не пишет владельцу сам** — ставит задачу Agent 8 (событие «проверить объект X на даты Y»).
Ответ владельца возвращается клиенту через Agent 7.

## 2. Каналы связи (единые контакты)

- **Один и тот же** WhatsApp-номер и TG-аккаунт для клиентов и собственников. Разделение:
  - WhatsApp: ярлык (label) `клиент` / `собственник` на чате;
  - Telegram: чат добавляется в папку `Клиенты` / `Собственники` (управляется userbot'ом через MTProto).
- **Telegram — личный аккаунт (userbot, Telethon/MTProto), НЕ бот.** Личный аккаунт вызывает больше доверия.
- WhatsApp: провайдер с API и синхронизацией с amoCRM (Wazzup / Green-API).
- Вся переписка зеркалится в amoCRM (синхронизация WA/TG ↔ amo), но поля квалификации агент пишет в сделку **явно**.

## 3. Мозг

- **Gemini 2.5 Flash через прямой API** (не MCP) — диалог, извлечение полей, упаковка офферов.
- Извлечение `Объект ID` из текста/подписи — regex (`#obj_YYYYMMDD_NNN`, `#YYYYMMDD_NNN`, голый ID), без LLM.
- Подбор альтернатив — детерминированные фильтры по Notion, LLM только формулирует ответ.

## 4. Диалог с клиентом

Мягкий, короткий, без анкеты из 7 вопросов подряд.

1. Клиент присылает пост/ссылку/ID → агент находит объект в Notion, подтверждает: название, район, цена.
2. Квалификация обязательна даже при выбранном объекте. Первым сообщением спрашиваем только суть:
   **даты заезда/выезда, сколько человек** (+ имя, если не представился).
3. Добивка остальных полей фразой:
   > «Возможно я предложу вам лучшие варианты, если скажете ещё желаемый район и ваш бюджет.»
4. Остальное (животные, срок) — по ходу диалога, точечно.
5. Перед показом альтернатив — **обязательно спросить**, нужны ли они.

Поля квалификации: даты заезда/выезда, срок, бюджет (+ допустимая погрешность), район,
кол-во человек, животные, имя.

Клиенту отправляем по объекту:
- ссылку на пост в TG-канале (`post_url_telegram`);
- ссылку на фото из R2 (колонка `Фото` в Notion);
- краткое «почему подходит» + цена + район.

## 5. Подбор альтернатив (фильтры, по жёсткости)

1. Пересечение дат / тип аренды; объект не `занято` по availability.
2. **Бюджет ±10%.** Если кандидатов мало — спросить клиента, какая погрешность по бюджету допустима, и расширить.
3. Район клиента (или соседние из whitelist).
4. Вместимость ≥ числа гостей (прокси — комнаты, пока нет отдельного поля).
5. Животные: если pets = да → подходят объекты `Можно с питомцами = да` **и объекты с пустым полем** (не указано ≠ нельзя).
6. Похожесть на выбранный объект: тип жилья, комнаты ±1.

## 6. Занятость объектов (availability)

Новые колонки в Notion (напротив объекта):

| Колонка | Тип | Значения |
|--|--|--|
| `availability_status` | select | `свободно` / `занято` / `уточняется` |
| `Занято до` | date | до какого числа занят |
| `Будущие брони` | rich_text | периоды будущих броней, если владелец сообщил |
| `availability_checked_at` | date | когда проверяли последний раз |
| `Свободно` | checkbox | отметка внешнего агента-актуализатора: галочка = доступность подтверждена; снятая = нет информации (НЕ «занято») |
| `Календарь` | url | где автоматически проверять доступность дат (pre-check Agent 8) |

Правила заполнения `Календарь` (в зависимости от источника объекта):
- объект с **Airbnb** → ссылка объявления дублируется в «Источник объявления» и в «Календарь»;
- объект от **управляющей компании** → в «Календарь» ссылка на их календарь занятости;
- календаря нет (**ручной** способ: FB Marketplace и т.п.) → «Календарь» пуст,
  доступность уточняется только сообщением владельцу через Agent 8.
Pre-check Agent 8 всегда идёт по «Календарь»; пусто — сразу пишем владельцу.

Поддерживаемые типы ссылок в `Календарь` (диспетчер `agent8/calendar_check.py`):

| Тип ссылки | Как проверяем | Статус |
|--|--|--|
| Google Sheets УК (`docs.google.com/spreadsheets/...#gid=вкладка_объекта`) | xlsx-экспорт: красная заливка = занято, жёлтая = «под вопросом» (уточнить у владельца), без заливки = свободно; вкладка объекта находится по gid | работает |
| iCal `.ics` (Airbnb ical, Booking, экспорт GCal) | скачиваем фид, пересечение ночей клиента с VEVENT | работает |
| Google Calendar (embed-ссылка с `src=`) | конвертация в публичный iCal-фид | работает |
| Airbnb-объявление | Playwright, чтение календаря страницы | этап 4 |

Проверяются **ночи** [check_in, check_out): выезд в день чужого заезда — не конфликт.
Даты за горизонтом календаря / сбой проверки → «неизвестно», пишем владельцу как обычно.

Правила согласования `Свободно` и `availability_status`:
- галочка стоит и статус не «занято» → объект считается подтверждённо свободным;
- Agent 8 при записи статуса сам синхронизирует чекбокс («свободно» → ставит, иначе снимает);
- внешний агент-актуализатор может работать только с чекбоксом — код это учитывает.

Самообучение системы: когда Agent 8 узнаёт от владельца, что объект занят, он **обязан** уточнить:
до какого числа занято, когда освободится, есть ли брони в будущем и на какие даты — и записать это в Notion.

**Занято на нужные даты — не тупик:** клиенту сообщаем, до какого числа объект занят и с какой
даты будет свободен («Этот объект занят до X, свободен с Y — подойдут такие даты?»).
Если клиента не устраивает — предлагаем альтернативы.

**Airbnb pre-check:** если `Источник объявления` — ссылка Airbnb, то **до** письма владельцу
Agent 8 проверяет открытые даты в календаре объекта по этой ссылке (headless-браузер Playwright,
как в Agent 1B; вариант — делегировать Clawbot/OpenClaw). Результат тоже пишется в колонки availability.
Если даты клиента закрыты в календаре — владельцу не пишем, клиенту сразу предлагаем альтернативы.

Pre-check распространяется и на **альтернативы**: перед тем как предлагать клиенту / писать
владельцу по альтернативному объекту с источником Airbnb, сначала проверяем его календарь.
Объекты с закрытыми датами отсеиваются, результат проверки пишется в availability-колонки.

## 7. Связь с владельцем: приоритет каналов и скрипты

Приоритет: **1) WhatsApp → 2) Telegram → 3) Airbnb DM → 4) FB Marketplace DM** (берём первый заполненный в Notion).

**WhatsApp / Telegram / FB Marketplace** — первое сообщение:
> «Здравствуйте! У меня есть клиент на ваше жильё, готов заселиться…» (+ даты, срок, бюджет, кол-во гостей, Объект ID для себя в CRM)

**FB Marketplace — дополнительно:** сразу попросить WhatsApp для связи. Полученный номер немедленно
записать в Notion (`WhatsApp контакт`) и в amoCRM, дальше общаться в WA.

**Airbnb — другой скрипт** (про клиента не пишем, контакт напрямую НЕ просим):
1. > «Здравствуйте! Меня интересует ваше жильё. Можно посмотреть дом?»
2. После ответа:
   > «Посмотрите моё изображение-аватар.» (на аватаре аккаунта — наши контакты WA и пр.)

Дальше ждём, что владелец сам выйдет на нас в WA/TG; общение продолжается там и фиксируется в CRM.

## 8. Воронка amoCRM — «Аренда — лиды»

Стадии:
1. **Новый лид**
2. **Квалификация**
3. **Подбор** (предлагаем варианты)
4. **Запрос владельцу** (ждём Agent 8)
5. **Согласование условий** (сдвиг дат/цены, клиент думает)
6. **Бронь подтверждена**
7. Закрывающие: **Успешно** / **Отказ** / **Не целевой**

Поля сделки: `Объект ID`, даты заезда/выезда, бюджет (+ допуск), район, гостей, животные, имя,
`source_channel`, `preferred_object_id`, `alternative_object_ids`, ссылка на Notion-страницу, ссылка на TG-пост.

Правила «никого не терять»:
- на сделке всегда тег `OBJ_{object_id}`;
- контакт клиента и контакт владельца привязаны к **одной** сделке;
- примечания с префиксом `[OBJ:20260708_001][CLIENT]` / `[OBJ:...][OWNER]`;
- 1 клиентский диалог = 1 активная сделка; смена объекта = обновление поля, не новая карточка;
- дедуп лидов по телефону / TG username.

SLA-таймеры: 2 ч без ответа владельца → эскалация менеджеру; 24 ч без ответа клиента → мягкий follow-up.
Handoff человеку: тег `need_human` + задача менеджеру (торг, жалоба, «хочу созвон»).

## 9. Стек

| Слой | Решение |
|--|--|
| WhatsApp | Wazzup / Green-API (+ синк с amo) |
| Telegram | Личный аккаунт через Telethon (MTProto), папки «Клиенты»/«Собственники» |
| Объекты | Notion API (те же поля, что у Agents 2/6) |

## 10. Порядок внедрения

1. Колонки availability в Notion + воронка и поля в amoCRM.
2. Agent 7: приём сообщения → извлечение ID → квалификация → карточка amo.
3. Матчинг альтернатив + отправка TG-ссылок и фото R2.
4. Agent 8: приоритет каналов, скрипты (включая Airbnb-скрипт), запись WA из Marketplace, Airbnb pre-check.
5. Замыкание цикла: ответ владельца → обновление availability в Notion → ответ клиенту.
